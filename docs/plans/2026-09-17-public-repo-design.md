# Public repository for the ODF Initial Download Generator

**Date:** 2026-09-17
**Status:** Design approved, not yet implemented
**Publishes to:** `github.com/mffcampos-cmyk/ODF-Initial-Download-Generator`

Prepare a public repository for this project, following the pattern already
used for the validator (`github.com/mffcampos-cmyk/ODF-Validator`, built by
`scripts/prepare_public_tree.py` in the private validator repo).

---

## Why the existing history cannot be published

Commit `4bfbc0e` (2026-08-28) removed
`samples/ARC/...DT_PARTIC_UPDATE...2025-10-17073219476000.xml`: a 60 KB
verbatim capture of a real-life ARC feed carrying roughly 115 participant
records with given and family names, passport names, birth dates of 2009-2011,
nationalities and IDs. The commit message reasons correctly that the records
are very probably synthetic, and equally correctly that this is an inference
rather than a documented fact.

Removing a file does not remove its blob. All 40 commits still contain it, and
a clone of that history hands it to anyone who asks `git log --all`. The same
is true of `ODF Generator.lnk`, which embedded one machine's SID, hostname and
user profile path before it was gitignored.

So the public repository is a **fresh tree with a fresh `git init` and a single
commit**. No history travels. This is the validator's pattern, adopted here for
a sharper reason than the validator had.

## What ships

Everything currently tracked by git, which was reviewed and approved
explicitly: the application, the 206-file `samples/` corpus, the tests, the six
documents under `docs/plans/`, the three front-end documents under `docs/`,
`B1_ROOT_CAUSE.md`, and the Windows launcher batch files.

## What does not ship

| Path | Reason |
|---|---|
| `.git` | See above. History does not travel. |
| `__pycache__`, `.pytest_cache`, `*.egg-info`, `node_modules` | Caches and build by-products. |
| `.superpowers/` | Agent scratch. |
| `output/` | Generated bundles. `samples/` is the committed corpus. |
| `docs/history.bundle`, `docs/recovery/` | Git bundles of the history being left behind. Shipping them would restore exactly what the fresh `git init` is for. |
| `ODF Generator.lnk` | Machine SID, hostname, profile path. Regenerated by `Install-ODF-Shortcut.bat`. |
| `task-2-report.md` | A placeholder pointing at git-ignored scratch. |
| `scripts/prepare_public_tree.py` and its test | The script exists to produce the tree; it has no function inside it. |

Most of these are already in `.gitignore`. The filter restates them anyway,
because the public tree is built by walking the working directory, not by
asking git what it tracks — and a `.gitignore` entry added tomorrow would
otherwise silently change what publishes.

## The guard

The validator's script counts rule definitions in both trees and refuses to
finish unless they match, because its filter could plausibly eat the rule set
while its own output still read like success. This project's filter removes
almost nothing, so that specific failure is unlikely. The likely failure here
is different: **a machine-specific path surviving into the published tree.**

The prepared tree is therefore checked on two axes, and a failure on either
aborts without leaving a publishable directory behind:

1. **Corpus intact.** Count `samples/**/*.xml` and `generator/**/*.py` in source
   and destination. Any mismatch aborts. (`--expect-samples 206` available as a
   second, independent assertion, in the spirit of `--expect-rules`.)
2. **No machine facts.** Grep every text file in the destination for the developer's home-directory prefix and for the sibling-checkout folder name, both defined in the script. Any
   hit aborts and names the file. This is the check that would have caught the
   current README, whose Setup section hardcodes both.

`tests/unit/test_public_tree_filter.py` exercises `should_drop` directly, as
the validator's does. Both files are excluded from the published tree.

## Making the validator installable

The generator imports `odf_validator` at module level in `selfcheck.py`,
`packload.py` and `packs.py`. It cannot start without it. Today that import is
satisfied by a sibling checkout at `../ODF Validator Webapp 2`, a path that
exists on one machine.

The public repository declares the validator as a real dependency:

```toml
dependencies = [
    ...,
    "odf-validator @ git+https://github.com/mffcampos-cmyk/ODF-Validator.git@<commit>",
]
```

**This does not work today.** `pip install` against a clone of the public
validator fails before it starts:

```
error: Multiple top-level packages discovered in a flat-layout:
       ['web', 'api', 'Rules', 'odf_validator'].
```

Setuptools refuses to guess. So the first task is in the *validator*
repository, not this one:

1. Add explicit package discovery to `ODF-Validator/pyproject.toml`:
   `[tool.setuptools.packages.find] include = ["odf_validator*"]`.
2. Add package data so `odf_validator/core_rules/core.yaml` travels inside the
   wheel. The engine-bundled `CORE_*` rules are not optional; an installed copy
   without them loads no core rules at all.
3. Verify `pip install git+...` into a clean environment, then import
   `odf_validator` and load a pack.
4. Push, and record the commit.
5. Mirror the same change into the private validator repository, so the two do
   not diverge at the next `prepare_public_tree.py` run.

The pin then does work that has been outstanding since the project began. The
current `pyproject.toml` carries a comment explaining that "validates clean" is
only meaningful against a specific validator revision, and that the revision is
"not recorded anywhere pip can see". After this change it is.

`packload.py` loses `_SIBLING_PACK` and its `../ODF Validator Webapp 2`
lookup. `ODF_PACK_DIR` keeps working and keeps its precedence.

## The vendored rule pack

`pip` installs the engine. It does not install `Rules/SYOG26`, which is a
directory in the validator repository rather than package data.

The public generator therefore carries its own copy: `Rules/SYOG26/` with
`pack.yaml`, the authored rules, the per-discipline rules, and the corrected
SYOG26 XSD — about 372 KB, all of it already public in `ODF-Validator`.

`Rules/SYOG26/PROVENANCE.md` records:

- the `ODF-Validator` commit the copy was taken from;
- that the XSD is deliberately not byte-identical to the IOC's published copy,
  carrying the `RecordBrokenType` to `pictureType` correction and the tightened
  header `@Time`, with the validator's explanation carried over — a reader of
  this repository must not have to find the other one to learn that;
- what the copy does **not** contain: the Common Codes workbook and the 25 Data
  Dictionaries, neither of which is redistributable from here;
- how to refresh it against a newer validator revision.

Pack resolution becomes: explicit argument, then `ODF_PACK_DIR`, then the
repo-local `Rules/<ODF_GAMES or SYOG26>`. The `SOLG28` stub travels the same
way and keeps reporting itself not ready, which remains true.

Drift between the vendored copy and the validator's is real and is not
prevented. It is made visible: the pinned commit appears in both
`PROVENANCE.md` and the dependency specifier, so the two can be compared by
reading them.

## Fetching the code tables

A vendored pack has rules and a schema but no code tables, and the generator
refuses to start against an empty pack — correctly, with `PackDirError`. Today
the fix is to install and run the validator web application, open Rulesets, and
apply downloaded sources. A public clone should not need a second application
to make the first one start.

New entry point:

```
python -m generator.sources [--pack SYOG26] [--all]
```

It reads `source.index_url` from the pack's `pack.yaml`, fetches through the
installed validator's `odf_validator.sources.sync`, applies what it fetched,
and runs `odf_validator.ingestion.builder.build_ruleset_pack` so the code
tables exist.

**By default it fetches the Common Codes workbook only.** That is what this
project needs: code membership, the EVENT_UNIT and LOCATION tables the event
structure is derived from, and the discipline function codes. The full import
additionally converts 25 Data Dictionary PDFs through `pdf-inspector` — slow,
and it would pull that toolchain in as a dependency of a project that never
reads a Data Dictionary directly. `--all` performs the full import for anyone
who wants the DD-derived obligations to fire.

`PackDirError` gains the sentence that makes it actionable: run
`python -m generator.sources`.

Built test-first. The unit test stubs the network and asserts the entry point
calls sync and ingestion against the right pack directory and reports what it
fetched; a real fetch stays a manual check.

## README

The Setup section is rewritten for someone who has just cloned:

1. `pip install -e ".[dev]"` — which now brings the validator with it.
2. `python -m generator.sources` — fetches and ingests the code tables.
3. `uvicorn api.app:app`.

No absolute paths from one machine, no sibling-checkout reference, no instruction to
install and operate a second application first. The `setx` and PowerShell
`$env:` blocks go with them.

What stays is what makes the current README worth reading, and it stays in
full: what "verified" covers and what it does not; the `ItemName` truncation
trade, its 150 over-length descriptions and the 86 unit codes it merges; why
`obligations.py` reports and never fills; the count overrides that have less
effect than expected and why; SOLG28's honest not-ready state.

Added: a section on what the repository ships and what it does not — the pack
it carries, the IOC documents it does not, and the one command that closes the
gap. This mirrors the validator's "First launch" section, which exists to stop
a new clone from looking broken when it is merely un-imported.

`Launch-ODF-Generator.bat`, `Install-ODF-Shortcut.bat` and
`README-shortcut.md` ship. The validator ships its `start_validator.bat` and
this is the same thing. `ODF Generator.lnk` never ships.

- The prepare script's own guards pass, and `--list-dropped` output is read

- The published tree is cloned fresh **in this session's cloud container** —
  a machine that has never seen the validator checkout, which is the only
